# บทที่ 4-13: guardrails ที่เขียนเอง

## แนวคิด
นอกจาก middleware สำเร็จรูป คุณเขียน **guardrail** (รั้วกั้น) เองได้ด้วย `createMiddleware` จุดแทรกที่ใช้บ่อย:

- `beforeModel`: ดักก่อนเรียกโมเดล (ตัวอย่างในบทนี้ตรวจทุกข้อความที่ผู้ใช้ส่งมาและโมเดลยังไม่ได้ตอบ และตัดอักขระความกว้างศูนย์ที่ใช้พรางคำ) เช่นปฏิเสธคำขอต้องห้ามโดย **ไม่เสียค่าโมเดลเลย**
- `afterModel`: ดักหลังโมเดลตอบ เช่นตรวจว่าคำตอบเผยความลับหรือไม่ แล้วแทนที่ (ข้อความใหม่ต้องใช้ `id` เดียวกับข้อความที่รั่ว เพื่อเขียนทับในประวัติ ไม่ใช่แค่ต่อท้าย ไม่งั้นความลับยังอยู่ในประวัติและถูกส่งให้โมเดลอีกในรอบถัดไป)

เมื่ออยากหยุดทั้งการรันและตอบเองทันที ให้ hook คืน `jumpTo: "end"` พร้อมข้อความ และต้องบอก middleware ว่ากระโดดไปได้ด้วย `canJumpTo`:

```ts
createMiddleware({
  name: "guard",
  beforeModel: {
    canJumpTo: ["end"],
    hook: async (state) => {
      if (ข้อความผู้ใช้ล่าสุดมีคำต้องห้าม) return { messages: [new AIMessage("ขออภัย")], jumpTo: "end" };
      return undefined;   // ผ่าน
    },
  },
})
```
guardrail แบบกฎ (คำต้องห้าม, regex) เร็วและแน่นอน ส่วน guardrail ที่ใช้โมเดลช่วยตัดสิน (classifier) ยืดหยุ่นกว่าแต่ช้ากว่าและพลาดได้

## ดูตัวอย่าง
`guard.ts` มีรายการคำต้องห้ามและคำเก็บเป็นความลับ ขาด hook ทั้งสองจุด

## ข้อควรจำ
- guardrail แบบนี้คุมสิ่งที่ `invoke()` คืนและสถานะปัจจุบัน แต่ข้อความที่โมเดลเพิ่งสร้างยังอาจอยู่ใน checkpoint ก่อนหน้าและในสตรีม (`stream`) ที่ส่งไปถึงผู้ใช้ก่อนถูกแทนที่ ถ้าความลับห้ามหลุดเด็ดขาด ให้ปกปิดก่อนเข้าโมเดล (บท 4-12) ไม่ใช่พึ่งการแก้ภายหลัง
- guardrail ขาเข้าประหยัดค่าโมเดล guardrail ขาออกกันความลับหลุด ใช้คู่กัน
- ข้อความที่ปฏิเสธควรบอกผู้ใช้ชัดเจนแต่ไม่เปิดเผยกติกาภายใน
