# บทที่ 5-13 เครื่องมือ SQL ที่ปลอดภัย

## แนวคิด

SQL agent ให้โมเดลเขียนคำสั่ง SQL แล้วรันกับฐานข้อมูลจริง นี่คือหนึ่งในงานที่อันตรายที่สุด: โมเดลอาจเขียน `DROP TABLE`, เดา schema ผิดแล้วดึงข้อมูลทั้งตาราง, หรือถูก prompt injection (บท 4-14) ให้อ่านตารางลับ หลักคือ **ป้องกันหลายชั้น (defense in depth)** ไม่เชื่อชั้นเดียว:

1. **ตัวตรวจคำสั่ง (บทนี้, ตรรกะล้วน):** คำสั่งเดียว ขึ้นต้นด้วย `SELECT` ไม่มีคอมเมนต์ ไม่มีคำสั่งแก้ข้อมูล อ่านได้เฉพาะตารางที่อนุญาต และจำกัดจำนวนแถว
2. **ธุรกรรมอ่านอย่างเดียว + timeout (บทนี้):** `BEGIN READ ONLY` และ `SET LOCAL statement_timeout` แม้ชั้น 1 หลุด ฐานข้อมูลก็ปฏิเสธการเขียน และคิวรีที่ช้าถูกตัด
3. **สิทธิ์ของผู้ใช้ฐานข้อมูล (ฝั่งโครงสร้างพื้นฐาน):** ให้ agent ใช้ role ที่มีแค่ `SELECT` บางตาราง ชั้นนี้สำคัญที่สุดเพราะไม่ต้องพึ่งโค้ดของเรา

ตัวตรวจแบบข้อความ **ไม่มีทางสมบูรณ์** (SQL มีเทคนิคหลบเยอะ) จึงเป็นแค่ชั้นแรกที่ปฏิเสธเคสที่เห็นชัดและให้ข้อความอธิบายแก่โมเดลเพื่อแก้คำสั่ง เมื่อไม่แน่ใจให้ปฏิเสธ (fail closed)

ข้อควรรู้ในตัวตรวจ:
- ตัดเนื้อใน string literal ออกก่อนตรวจคำ (`WHERE name = 'delete'` ต้องไม่ถูกปฏิเสธ)
- เครื่องหมาย `;` ท้ายคำสั่งตัวเดียวได้ ที่อื่นแปลว่าหลายคำสั่ง
- `FROM a, b` (คั่นด้วยจุลภาค) หลบการตรวจตารางที่สอง จึงปฏิเสธ ให้ใช้ `JOIN`
- เรียกฟังก์ชันใน `FROM` (เช่น `generate_series`) ปฏิเสธ

## 1. ลองเติมช่องเดียว

เปิด [`sqlGuard.ts`](./sqlGuard.ts) แล้วเติมข้อ 1: เติมส่วนหลักของบท (เครื่องมือ SQL ที่ปลอดภัย) รันจากโฟลเดอร์หลักของโปรเจกต์ บทนี้ใช้ Postgres: เปิดฐานข้อมูลด้วย `docker compose up -d --wait` และตั้ง `DATABASE_URL` ใน `.env` ก่อนรัน

```sh
pnpm lesson 5-13
```

ในไฟล์ข้อ 1 มี **แนวทาง** เป็นโค้ดที่คอมเมนต์ไว้ เอา `//` ออกแล้วแทนที่ `todo(1)` ได้เลย แต่ลองอ่านก่อนว่าแต่ละบรรทัดทำอะไร

`sqlGuard.ts` ให้ `stripLiterals`, `Db` และตัวประกอบ `validateSql` ไว้ ส่วนอื่นของบทนี้เขียนไว้ให้แล้ว ขาดแค่ข้อ 1

โค้ดตามแนวทาง:

```ts
const s = stripLiterals(sql).trim();
if (s === "") return "คำสั่งว่างเปล่า";
if (s.includes("'")) return "string ไม่ปิดเครื่องหมายคำพูด";
if (s.includes("--") || s.includes("/*")) return "ห้ามมีคอมเมนต์ในคำสั่ง";
if (s.includes('"')) return "ห้ามใช้ชื่อในเครื่องหมายคำพูดคู่";
const semi = s.indexOf(";");
if (semi !== -1 && semi !== s.length - 1) return "ห้ามมีหลายคำสั่ง";
if (!/^select\b/i.test(s)) return "อนุญาตเฉพาะคำสั่ง SELECT";
return null;
```

## 2. ผลที่ได้

ผลที่รันจากเฉลย

```text
  realRows: 3,
  realLeak: 'ไม่อนุญาตให้อ่านตาราง demo_secrets',
  deleteMsg: 'cannot execute DELETE in a read-only transaction',
  sleepMsg: 'canceling statement due to statement timeout',
  remaining: '5'
✅ คำสั่งปกติผ่าน และได้ LIMIT ต่อท้าย
✅ ต้องเป็น SELECT เท่านั้น
✅ หลายคำสั่ง คอมเมนต์ และชื่อในเครื่องหมายคำพูดคู่ถูกปฏิเสธ
✅ เนื้อใน string literal ไม่ถูกตีความเป็นคำสั่ง/คอมเมนต์/เซมิโคลอน
✅ string ไม่ปิดถูกปฏิเสธ
✅ คำต้องห้ามเป็นคำเต็มเท่านั้น: ชื่อคอลัมน์ที่มีคำนั้นเป็นส่วนหนึ่งไม่โดน
✅ อ่านได้เฉพาะตารางที่อนุญาต (รวม JOIN และ subquery) ไม่สนตัวพิมพ์
✅ เรียกฟังก์ชันใน FROM ปฏิเสธ
✅ คั่นหลายตารางด้วยจุลภาคปฏิเสธ (กันหลบการตรวจตารางที่สอง)
✅ applyLimit: เติม/ลด LIMIT ไม่เกินเพดาน และตัด ; ท้าย
✅ runReadOnly: BEGIN READ ONLY → SET LOCAL timeout → คิวรี → ROLLBACK
✅ runReadOnly: คิวรีล้มก็ยัง ROLLBACK และโยน error เดิม
✅ runReadOnly: timeout ที่ไม่ใช่จำนวนเต็มบวกถูกปฏิเสธก่อนแตะฐานข้อมูล (กันฉีดผ่าน SET)
✅ Postgres จริง: SELECT ปกติได้เพดาน 3 แถว ตารางลับถูกปฏิเสธ
✅ Postgres จริง: ชั้น 2 กัน DELETE และตัด pg_sleep ด้วย timeout ข้อมูลยังอยู่ครบ
```

สิ่งที่ได้: สร้างเครื่องมือ SQL ที่ปฏิเสธคำสั่งอันตรายหลายชั้น และอธิบายเหตุผลให้โมเดลแก้เอง

## ข้อควรจำ

- ตัวตรวจข้อความ + role สิทธิ์ต่ำ + ธุรกรรมอ่านอย่างเดียว ต้องใช้ครบ
- อย่าส่งข้อความ error ของฐานข้อมูลดิบให้ผู้ใช้ปลายทาง (อาจเผยโครงสร้าง)
- แถวที่คืนอาจมีข้อมูลส่วนบุคคล ผ่านบท 4-13/4-14 ก่อนแสดง
