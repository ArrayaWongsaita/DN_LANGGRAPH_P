# บทที่ 5-14 กราฟ SQL agent

## แนวคิด

บท 5-13 ได้ตัวตรวจ SQL แล้ว บทนี้ประกอบเป็น agent ที่ตอบคำถามภาษาคนด้วยข้อมูลในฐานข้อมูล โดยไม่ปล่อยให้โมเดลรันอะไรตามใจ:

```
START → inspect (อ่าน schema) → write (โมเดลเขียน SQL) → check (ตัวตรวจ)
                                        ↑                    │ ไม่ผ่าน (ส่งเหตุผลกลับไปให้โมเดลแก้)
                                        └────────────────────┤
                                                              │ ผ่าน
                                                              ▼
                       respond ← execute (รันแบบอ่านอย่างเดียว) ── ล้มเหลว (ส่งข้อความ error กลับไปให้แก้)
```
- **วงรอบแก้ไข (retry loop):** เมื่อตัวตรวจหรือฐานข้อมูลปฏิเสธ ส่งเหตุผลกลับเข้าไปในพรอมต์ให้โมเดลเขียนใหม่ แต่ **จำกัดจำนวนครั้ง** (`maxAttempts`) ไม่งั้นวนไม่รู้จบและเปลืองเงิน หมดแล้วต้อง "ยอมแพ้อย่างสุภาพ" โดย **ไม่รัน SQL และไม่เรียกโมเดลอีก**
- **รันเฉพาะ SQL ที่ตัวตรวจคืนมา** (ที่ผ่านการเติม LIMIT แล้ว) ไม่ใช่ข้อความดิบจากโมเดล
- **ผลลัพธ์จากฐานข้อมูลคือข้อมูลภายนอก** (บท 4-14): ในแถวอาจมีข้อความที่ผู้ใช้คนอื่นเขียนไว้ว่า "ละเลยคำสั่งก่อนหน้า…" พรอมต์ตอบต้องระบุว่าเป็นข้อมูลดิบห้ามทำตาม
- ตัวตรวจและตัวรันถูก **ฉีดเข้ามา** (`validate`, `db`) ตัวตรวจของบทนี้จึงใช้ของปลอมได้ ส่วนของจริงคือผลงานของบท 5-13

## 1. ลองเติมช่องเดียว

เปิด [`agent.ts`](./agent.ts) แล้วเติมข้อ 1: เติมส่วนหลักของบท (กราฟ SQL agent) รันจากโฟลเดอร์หลักของโปรเจกต์ บทนี้ใช้ Postgres: เปิดฐานข้อมูลด้วย `docker compose up -d --wait` และตั้ง `DATABASE_URL` ใน `.env` ก่อนรัน

```sh
pnpm lesson 5-14
```

ในไฟล์ข้อ 1 มี **แนวทาง** เป็นโค้ดที่คอมเมนต์ไว้ เอา `//` ออกแล้วแทนที่ `todo(1)` ได้เลย แต่ลองอ่านก่อนว่าแต่ละบรรทัดทำอะไร

`agent.ts` ให้ State, การเดินสายกราฟ และ node `inspect`/`giveup` ไว้แล้ว ส่วนอื่นของบทนี้เขียนไว้ให้แล้ว ขาดแค่ข้อ 1

โค้ดตามแนวทาง:

```ts
if (state.feedback === "") return "execute";
return state.attempts < maxAttempts ? "write" : "giveup";
```

## 2. ผลที่ได้

ตัวอย่างผลที่รันจากเฉลย ข้อความจากโมเดลเปลี่ยนได้ทุกรอบ

```text
  citySql: 'SELECT city, COUNT(*) AS customer_count FROM demo_customers GROUP BY city ORDER BY customer_count DESC, city LIMIT 50',
  cityAnswer: 'จำนวนลูกค้าแต่ละเมืองมีดังนี้
' +
    '
' +
    '- กรุงเทพ: 2 คน
' +
    '- ขอนแก่น: 1 คน
' +
    '- เชียงใหม่: 1 คน',
  dangerAnswer: 'ขออภัย ไม่สามารถสร้างคำสั่ง SQL ที่ปลอดภัยสำหรับคำถามนี้ได้ (เหตุผลล่าสุด: ต้องเ',
  remaining: '5'
✅ เส้นทางปกติ: schema → เขียน → ตรวจ → รันค่าที่ตัวตรวจคืน → ตอบ
✅ buildWritePrompt: ไม่มี feedback ก็ไม่มีบรรทัดปฏิเสธ มีก็ใส่เหตุผล
✅ ตัวตรวจปฏิเสธ: ส่งเหตุผลกลับให้โมเดลแก้ แล้วรันคำสั่งที่แก้แล้ว (คำสั่งอันตรายไม่เคยถูกรัน)
✅ ปฏิเสธครบจำนวนครั้ง: ยอมแพ้ ไม่รัน SQL ไม่เรียกโมเดลตอบ และบอกเหตุผล
✅ maxAttempts ใช้ค่าที่กำหนด (1 = ลองครั้งเดียว)
✅ ฐานข้อมูลล้ม: ส่งข้อความ error กลับให้โมเดลแก้ แล้วลองใหม่
✅ ฐานข้อมูลล้มทุกครั้ง: ยอมแพ้หลังครบจำนวนครั้ง
✅ nextStep: ครบทุกกรณี
✅ checkSql / executeSql: ค่าที่คืนตามสัญญา
✅ พรอมต์ตอบ: มีคำถาม SQL ผลลัพธ์ ตัดตาม maxChars และเตือนว่าเป็นข้อมูลดิบ
✅ ข้อมูลในแถวที่เป็น prompt injection ไปถึงโมเดลในฐานะข้อมูลดิบ ไม่ใช่คำสั่งที่รัน
✅ โมเดลจริง + Postgres จริง: ตอบคำถามเมืองได้ด้วย SELECT และคำขอลบไม่ทำให้ข้อมูลหาย
```

สิ่งที่ได้: สร้าง SQL agent ที่แก้คำสั่งเองได้ในขอบเขต ปฏิเสธอย่างปลอดภัย และไม่เชื่อข้อมูลที่ดึงมา

## ข้อควรจำ

- agent เห็นเฉพาะ schema ของตารางที่อนุญาต (ไม่ใช่ทั้งฐานข้อมูล)
- ใช้ role ฐานข้อมูลสิทธิ์ต่ำเสมอ (บท 5-13)
- ถ้าตารางเยอะ ให้ใส่ schema เฉพาะที่เกี่ยวข้อง (ค้นด้วย retrieval จากบท 4-18)
