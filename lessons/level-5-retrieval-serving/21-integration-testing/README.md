# บทที่ 5-21 Integration test ที่เรียกโมเดลจริงแบบ "เลือกเปิด"

## แนวคิด

บทเรียนส่วนใหญ่ในคอร์สนี้ใช้โมเดลปลอมในส่วนตรวจ: เร็ว ฟรี ผลคงที่ แต่ **ไม่รู้เลยว่าโมเดลจริงตอบรูปแบบที่โค้ดคาดไหม** (เช่นคืน JSON ตาม schema ไหม เรียก tool ถูกชื่อไหม) จึงต้องมี **integration test** อีกชั้นที่เรียกของจริง ซึ่งต่างจาก unit test ปลอมมาก:

| | unit test (โมเดลปลอม) | integration test (โมเดลจริง) |
|---|---|---|
| ผล | คงที่ ทุกครั้งเหมือนกัน | **เปลี่ยนได้ทุกครั้ง** (non-deterministic) |
| ค่าใช้จ่าย/ความเร็ว | ฟรี มิลลิวินาที | เสียเงิน/โควตา วินาที |
| ต้องมี key/เครือข่าย | ไม่ | ใช่ |
| รันเมื่อไร | ทุกครั้ง (CI ทุก commit) | **เมื่อเลือกเปิดเท่านั้น** (เช่นก่อน release, รายคืน) |

หลักการเขียนที่ดี (บทนี้ทำเป็นฟังก์ชันช่วยที่ทดสอบได้):
1. **ข้ามอัตโนมัติถ้าไม่พร้อม:** ไม่ตั้ง `RUN_LIVE=1` หรือไม่มี key ของ provider ที่เลือก → ข้าม (skip) พร้อมบอกเหตุผล ห้ามทำให้ `pnpm test` ของคนอื่นล้ม
2. **ตรวจแบบทนความต่าง:** อย่าเทียบข้อความเต็ม ตรวจว่า "มีคำสำคัญ" หลังจัดรูปแบบ (ไม่สนตัวพิมพ์/ช่องว่าง) หรือตรวจโครงสร้าง (มี tool call ถูกชื่อ)
3. **ลองซ้ำเฉพาะเมื่อควร:** ผลหลุดเกณฑ์เป็นครั้งคราวลองใหม่ได้ แต่ **ผิดสิทธิ์ (401/403) ต้องหยุดทันที** อย่าเผาโควตาซ้ำ
4. **มีงบ:** จำกัดจำนวนการเรียกจริงต่อรอบ กันลูปรั่วเงิน

รูปแบบที่ใช้กับ vitest (ให้ไว้ในโปรเจกต์ของคุณ ไม่ใส่ในบทเรียน):

```ts
const status = liveStatus(process.env);
describe.skipIf(!status.enabled)(`live (${status.reason})`, () => {
  test("agent เรียก tool บวกเลข", async () => {
    const answer = await eventually(async () => { /* เรียก agent จริง */ ; assert(mentions(text, ["5"])) });
  }, 60_000);
});
```

## 1. ลองเติมช่องเดียว

เปิด [`live.ts`](./live.ts) แล้วเติมข้อ 1: เติมส่วนหลักของบท (Integration test ที่เรียกโมเดลจริงแบบ "เลือกเปิด") รันจากโฟลเดอร์หลักของโปรเจกต์ บทนี้เรียกโมเดลจริง ตั้ง provider และ API key ใน `.env` ตาม [บท 1-02](../../level-1-basics/02-llm-config/README.md) ก่อนรัน

```sh
pnpm lesson 5-21
```

ในไฟล์ข้อ 1 มี **แนวทาง** เป็นโค้ดที่คอมเมนต์ไว้ เอา `//` ออกแล้วแทนที่ `todo(1)` ได้เลย แต่ลองอ่านก่อนว่าแต่ละบรรทัดทำอะไร

ในไฟล์มีส่วนอื่นของบทนี้เขียนไว้ให้แล้ว ขาดแค่ข้อ 1

โค้ดตามแนวทาง:

```ts
const haystack = normalize(text);
const wanted = needles.map(normalize).filter((n) => n !== "");
if (wanted.length === 0) return false;
return mode === "all" ? wanted.every((n) => haystack.includes(n)) : wanted.some((n) => haystack.includes(n));
```

## 2. ผลที่ได้

ตัวอย่างผลที่รันจากเฉลย ข้อความจากโมเดลเปลี่ยนได้ทุกรอบ

```text
สถานะ: ข้าม: ตั้ง RUN_LIVE=1 เพื่อเปิด
✅ liveStatus: ไม่ตั้ง RUN_LIVE=1 → ข้ามพร้อมเหตุผล (แม้มี key)
✅ liveStatus: provider เริ่มต้น groq ต้องมี GROQ_API_KEY ยาวพอ (ยาว 10 พอดีผ่าน)
✅ liveStatus: ใช้ key ของ provider ที่เลือกเท่านั้น, LLM_PROVIDER ว่างใช้ groq, ไม่รู้จักก็ข้าม
✅ liveStatus: เหตุผลไม่เคยมีค่าของ key
✅ normalize: ไม่สนตัวพิมพ์/ช่องว่าง/อักขระความกว้างศูนย์ (ทั้งช่วง) และ NFC
✅ mentions: any/all และทนช่องว่างที่โมเดลเติมในภาษาไทย
✅ mentions: needles ว่าง หรือมีแต่สตริงว่าง ต้องไม่ผ่านโดยบังเอิญ
✅ classifyError: จัดประเภทตามสถานะและข้อความ
✅ eventually: สำเร็จครั้งแรกเรียกครั้งเดียว; ผลหลุดเกณฑ์ครั้งคราวลองซ้ำจนผ่าน
✅ eventually: ครบจำนวนครั้งแล้วยังล้ม → error ที่บอกจำนวนครั้งและสาเหตุสุดท้าย
✅ eventually: ผิดสิทธิ์ (401/403) หยุดทันที ไม่เผาโควตา และโยน error เดิม
✅ eventually: รอระหว่างครั้งตาม delayMs แต่ไม่รอหลังครั้งสุดท้าย
✅ createBudget: ใช้ได้ตามงบแล้วหยุด
✅ โมเดลจริง (เฉพาะเมื่อเปิด RUN_LIVE=1): ได้คำตอบที่มี 5
```

สิ่งที่ได้: ออกแบบ integration test ที่ข้ามเองเมื่อไม่พร้อม ทนความไม่แน่นอนของโมเดล และไม่เผาโควตา

## ข้อควรจำ

- unit test ปลอมยังเป็นฐาน integration test เป็นชั้นเสริม ไม่ใช่ตัวแทน
- อย่าใส่ key ในไฟล์ทดสอบหรือ log; อ่านจากสภาพแวดล้อมเท่านั้น
- เก็บผลจริงที่เจอบ่อยเป็นกรณีทดสอบปลอมใหม่ (ปิดช่องว่างระหว่างสองชั้น)
